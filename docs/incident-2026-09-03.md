# September 2026 service outage

## Summary

The Raspberry Pi and HT813 remained physically healthy. The call database has
no entries after July 26, while the surviving journal begins at the September
3 boot, so the original moment calls stopped is not present in the available
logs. The September boot followed an unclean shutdown and exposed two
independent defects that prevented reliable recovery:

1. The Asterisk service rebuilt its container image during every boot. The
   Pi's clock was stale, so TLS certificate validation failed until NTP
   synchronized. A later build attempt exceeded the five-minute service
   timeout.
2. The active PJSIP configuration expected the HT813 to register dynamically,
   while the ATA was configured for direct-IP peering with SIP registration
   disabled. The old in-memory static contacts had hidden this mismatch until
   Asterisk restarted.

## Evidence timeline

| Time | Evidence | Meaning |
|---|---|---|
| July 26 | Last call database record | No later call reached the logging path; no journal from that date survives to explain why. |
| September 3, boot | ext4 performed orphan cleanup | The preceding shutdown was unclean, consistent with lost power or a forced reset. |
| Boot + seconds | Docker rejected the base image certificate because the system clock was weeks behind | Building at boot coupled telephony startup to correct time and Internet access. |
| 10:28 | NTP corrected the clock | Docker could access the registry again. |
| 10:28–10:33 | Container build exceeded `TimeoutStartSec=300` | Asterisk remained unavailable through another failed start. |
| 10:34–10:38 | Automatic retry completed the build | Asterisk finally started about ten minutes after boot. |
| After restart | Asterisk reported zero contacts and both HT813 endpoints unavailable | The newly loaded registration-only AORs did not match the ATA's direct-peer mode. |
| Diagnostic capture | HT813 answered ARP and HTTP, but sent no REGISTER traffic | Hardware and Ethernet were healthy; dynamic registration was not part of the active ATA behavior. |
| Repair | Static FXO and FXS contacts answered SIP OPTIONS | Both endpoints returned to `Available`. |

The available journal contains only the current boot, so it cannot prove why
calls originally stopped or what caused the later power interruption. The
filesystem recovery record confirms an unclean shutdown before the September
boot; it does not identify whether that was the original failure trigger.

## Corrective actions

- Restored static AOR contacts for both direct-IP HT813 ports.
- Added regression tests requiring those contacts.
- Removed image builds and registry access from the systemd boot path.
- Pinned the Compose project name so deployment-directory changes do not leave
  conflicting containers.
- Configured systemd to restart Asterisk after clean or failed container exits.
- Moved live execution to `/opt/teleblock/app`, separate from the editable
  source checkout.
- Added an explicit deployment helper and kept builds behind `--build`.
- Protected `.env`, call data, logs, and live SIP credentials from source sync.
- Tightened the deployed `.env` file mode to `0640`.

## Further improvements

- Put the Pi and HT813 on a small UPS to avoid abrupt filesystem shutdowns.
- Add a systemd timer that qualifies both PJSIP endpoints and alerts after
  repeated failures.
- Add external heartbeat monitoring for the FastAGI TCP port and both SIP
  contacts.
- Back up the SQLite database and validate it periodically with
  `PRAGMA integrity_check`.
- Export a redacted HT813 configuration backup after every intentional change.
- Retain enough persistent journal storage to preserve several boot cycles.

Grandstream documents both registered-account operation and direct peering.
For direct peering, SIP registration is disabled and outgoing calls without
registration are enabled; the SIP server must therefore keep static peer
contacts. See the [HT813 administration guide](https://documentation.grandstream.com/knowledge-base/ht813-administration-guide/)
and [direct peering guide](https://documentation.grandstream.com/knowledge-base/peering-ht8xx-with-ht813/).
